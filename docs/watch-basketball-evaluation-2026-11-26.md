# 手表端新增「篮球」计分：方案评审与决策评估

- **日期**：2026-11-26
- **状态**：未立项（评估与结论沉淀，供后续产品/设计/开发 Agent 直接查阅）
- **关联原型**：`demo/watch-basketball-score-proposals.html`
- **触发背景**：有用户反馈「手表上没有篮球」；团队讨论手表端增加篮球计分的可行性，并明确前提：**`+1`、`+2`、`+3` 一定要显性显示出来**；同时倾向**不带计时和节次**。

---

## 一、核心结论

1. **当前决策建议：先按住观察，不必急于立项**
   - 篮球属于强身体对抗运动，场上球员大多不戴手表，真实戴表计分频次远低于羽/乒/网/匹克球/台球等非对抗项目；此前代码有意将常规篮球排除在手表首页之外，本身是合理的克制。
   - 如果目前只是零星 1~2 条用户反馈，此时引入会打破「手表首页运动项目全支持双端联动」的一致性，并引入方表/圆表特化布局的长期维护成本，投入产出比偏低。
   - 建议先记入需求池观察反馈频次；若后续确认为持续高频诉求，再按下方**「最小无痛切口」**推进。

2. **现有原型 `demo/watch-basketball-score-proposals.html` 存在 4 个硬伤，不建议直接照搬**
   - 未真正满足「`+1 / +2 / +3` 显性显示」；
   - 圆表 R2 实测几何有误（底部 `3` 分格实际超出圆弧 `33.7 dp`，并非文中声称的 `1.5 dp`）；
   - 「长按减分 + 中间常驻撤销圆点 + 暗色低透明底色 + 居中顶栏」与现有 Watch 工程的手势、菜单、系统时钟避让和室外可读性规范冲突；
   - 落地要点误读了旧注释，对当前仓库现状判断不准确。

3. **若后续决定立项：推荐「最小无痛切口」**
   - **定位**：手表独立纯计分器（不带计时、不带节次、**首版不做手机 ↔ 手表联动**）；
   - **入口**：首页单入口「篮球」，直接进入显性 **`+1` / `+2` / `+3`** 计分板（3x3 用户只点 `+1`/`+2` 即可，首版不拆 5v5 / 3x3 模式弹窗和配置页）；
   - **界面**：**比分展示（只读）与 `+1 / +2 / +3` 按键彻底分离**，带明确 `+` 号；方表走 3×2 显性按键，圆表走贴弧收腰 3×2（0 裁切）；
   - **手势**：100% 沿用现有统一手势（轻点加分 / 下滑撤销 / 长按出菜单 / 右滑退出），不做长按减分和常驻撤销圆点。

## 二、对现有原型（`demo/watch-basketball-score-proposals.html`）的评审

### 1. 可取之处
- 坚持**一步直达记分**（不走类似斯诺克的二级弹窗）；
- 考虑了 5v5 与 3x3 分值差异；
- 意识到 466×466 圆表不能直接照搬方表竖排比例；
- 注意到红蓝视觉亮度差并做了亮度补偿。

### 2. 四大硬伤

#### （1）未满足「`+1 / +2 / +3` 一定要显示出来」
- **`+1` 被弱化隐藏**：原型把 `+1` 合并进比分展示区，仅在比分下放一行 `10 pt`、`rgba(255,255,255,0.6)` 小灰字 `＋1`，无按钮边界感，需靠「首次呼吸高亮 1.5s」引导解释（见原型第 287 行）。
- **`2` / `3` 缺少 `+` 号**：下方按键只显示裸数字 `2`、`3`，运动中一瞥易与节次、犯规、暂停等统计数字混淆（圆表 R2 的 2×2 网格尤为明显）。
- **高频假设与实战相反**：原型第 213 行以「罚球是最常按的一档」为理由给 `+1` 分配最大面积（40%），但 5v5 实战中最高频是 **`+2`**，其次 `+3`，业余球局罚球 `+1` 反而最少；只有 3x3 中 `+1` 最高频，但 3x3 并无 `+3`。

#### （2）圆表 R2 实测几何计算错误
按原型第 146–178 行 CSS 验算（直径 `466 px`，半径 `R = 233 px`，圆心 `(233, 233)`，`--sc: 1.177` → `1em = 18.832 px`）：
- 上方 `.r2-score` 顶外角在 `(71, 61)`，距圆心 `236.1 px`，确实超出约 `3.1 px`（`1.55 dp`）；
- **但下方 `.r2-grid` 撑满全宽**（左边距 `16 px`，底边落至 `y ≈ 440.6 px`），左下角 `(16, 440.6)` 距圆心：
  $$\sqrt{(233 - 16)^2 + (440.6 - 233)^2} \approx 300.3\text{ px}$$
  **实际超出圆弧 `67.3 px`（约 `33.7 dp`）**，而非文中声称的「四边全在圆内，外角最多贴弧 1.5 dp」。在 `y = 440.6` 处圆的弦宽仅 `212 px`（每侧 `106 px`），`3` 分格底边超过一半宽度已被圆弧裁切。底部 `.toast` 同样有被底弧切字风险。

#### （3）与当前 Watch 工程交互、视觉规范冲突
- **长按手势冲突（致命）**：全端计分板统一使用 `WatchScoreboardGestureModifier`（`jifenWatch Watch App/Components/WatchScoreboardComponents.swift:1161-1196`）：**长按 0.5s 打开菜单**（撤销/重置/结束比赛/布局切换/手表接管）、**下滑撤销**、**右滑退出**。原型将长按用于「减分」，却未给出菜单与结束比赛入口。
- **中间常驻撤销圆点多余且易误触**：已有「下滑撤销」与菜单撤销，在两个比分之间塞入 `20 pt` 圆点既易在点比分时误触，又挤压三位数比分空间。
- **Apple Watch 顶栏时钟撞车 & 只读计时无闭环**：watchOS 右上角常驻系统时钟（工程统一预留 `WatchLayout.scoreboardTopNameInset = 40`，见 `WatchTheme.swift:13`）。原型顶栏仅 `20 pt` 且居中排布 `第 1 节 · 07:42`，在 41mm 上会与系统时钟重叠；同时顶栏标为「只读」，未交代本机开赛时计时启停与节次切换路径。
- **室外球场可读性下降**：现有手表两队计分板统一使用高饱和实色底（`WatchTheme.teamRed = #E53935`、`WatchTheme.teamBlue = #1E88E5`）+ 白色大字，室外强光下辨识度高；原型改为黑底叠 `10%~25%` 透明渐变 + 红蓝彩字，室外反光下对比度显著变差。

#### （4）对代码库现状的误判
原型第 284 行称「只有手机发起的联动能开历史板」，系被旧注释误导。实际核实结果见下文第三节。

## 四、做与不做的决策负担清单

即使明确**不带计时和节次**，引入手表篮球仍会带来以下 4 类负担：

1. **双端联动的一致性两难（最大决策负担）**
   - 目前手表首页除计数器外，所有运动项目均支持手机↔手表联动。
   - **不接联动**：架构干净，但打破统一心智，用户会追问为何手机篮球（含投屏）连不到手表；
   - **强行接联动**：手机端篮球是完整裁判台（节次、比赛钟、24 秒、犯规、暂停、加时），手表端却是无计时纯计分，双端状态不对等会引出大量接管/同步/到时边界问题，研发与测试成本翻 3~5 倍。
2. **多形态与双端布局维护负担**
   - 现有羽/乒/网/足均是「两块大点击区」，方表/圆表与横屏/竖屏几乎零成本复用；
   - 篮球主屏是「比分 + 6 个显性加分键」，方表（Apple Watch 41/45/49mm）与圆表（华为/Wear OS 466×466）必须维护两套截然不同的几何布局，且需考虑横/竖屏设置及 iOS Watch ↔ 鸿蒙 Watch 对齐成本。
3. **必然发生的需求蔓延**
   - 上线纯计分后，用户大概率会继续追要「节次」「10/12 分钟倒计时」「3x3 21 分自动结束」；要么持续承受拒绝/解释成本，要么逐步膨胀成另一个 1200+ 行状态机（类似 `WatchFootballScoreView.swift`）。
4. **记录回传与回归测试成本**
   - 需补齐 `WatchLinkMenuSupport.swift:471` 的 `hasNoSetLayer`，并验证无节次/无比赛钟的手表记录回传手机后，在历史详情、时间轴、修正弹窗和云同步中的表现正常；同时增加 Watch 多尺寸 + 多语言回归用例。

## 五、若后续立项的推荐落地规格（最小无痛切口）

### 1. 范围锁定（首版严格不越界）
- **仅手表独立纯计分**：不带计时、不带节次、首版不接手机↔手表联动（完赛记录仍走 `WatchRecordManager` 正常回传手机）。
- **单入口兼容 5v5 与 3x3**：首页仅新增「篮球」一项，直接进 **`+1` / `+2` / `+3`** 计分板（3x3 用户直接只点 `+1`/`+2` 即可，免去模式弹窗、setup 配置和双类型分支）。
- **统一手势**：复用 `WatchScoreboardGestureModifier`——**轻点 `+1/+2/+3` 加分、下滑撤销（配 `watchUndoToast`）、长按呼出 `WatchScoreboardMenuOverlay`（撤销/重新开始/结束比赛）、右滑退出并挂载 `WatchResumeSession`**。
- **高对比视觉**：沿用实色/高饱和红蓝（`WatchTheme.teamRed` / `WatchTheme.teamBlue`）+ 白色粗体字，保障室外篮球场强光可读性。

### 2. 布局与几何规格（比分与显性 `+1/+2/+3` 分离）

#### A. 方表（Apple Watch 41mm / 45mm / 49mm）
- **顶部安全留白**：无计时/节次时，左上/顶部无需额外状态条，只需为系统时钟保留顶部安全区（避免队名撞钟）。
- **上方纯比分展示区（只读，左红右蓝）**：45mm 高约 `56 pt`（41mm 约 `48 pt`），显示队名 + 大比分（三位数自动缩字号），不承载点击加分。
- **下方 3×2 显性加分区（左红右蓝，明确带 `+` 号）**：
  - 45mm（`198 × 242 pt`）：每键约 **`94 × 50 pt`**；
  - 41mm（`176 × 215 pt`）：每键约 **`83 × 44 pt`**（全部 ≥ 44 pt 触控标准）；
  - 按钮文字明确写 **`+1`、`+2`、`+3`**，可用细微明度差或分割线区分三档，零学习成本。

#### B. 圆表（466 × 466 px ≈ 233 × 233 dp，华为 / Wear OS）
顺应圆弧弦宽（上窄 → 中腰最宽 → 下窄），确保四边与圆角 100% 落在圆内（0 裁切）：
- **推荐：贴弧收腰 3×2（左红右蓝）**
  - 上腰（`y: 52~132 px`，总宽 `300 px`）：红蓝并排纯比分展示区（每队约 `73 × 40 dp`）；
  - 中下腰三行显性加分键（`y: 140~394 px`，每行高 `80 px = 40 dp`，行距 `7 px`）：
    - 第 1 行 **`+1` | `+1`**：总宽 `410 px`（每键 `100 × 40 dp`）；
    - 第 2 行 **`+2` | `+2`**：总宽 `410 px`（每键 `100 × 40 dp`）；
    - 第 3 行 **`+3` | `+3`**：按弦宽主动收窄至总宽 **`304 px`**（每键 **`74 × 40 dp`**）；
  - 验算最下角 `(x = 81, y = 394)`：距圆心 `sqrt(152² + 161²) = 221.4 px < 233 px`，留有 `11.6 px`（`5.8 dp`）安全余量，**0 裁切**；底部余留 `72 px` 供弧线安全区与短 Toast 使用。
- **备选：上下分队 + 圆心腰带横排 `+1 / +2 / +3`**
  - 上半圆红队（顶弧比分 + 圆心上方横排 `+1` `+2` `+3`），下半圆蓝队（圆心下方横排 `+1` `+2` `+3` + 底弧比分），6 键全落直径最宽处（每键约 `66 × 38 dp`），天然契合上下布局；缺点是两队比分纵向分布，横向扫视对比稍弱于左红右蓝。

### 3. 工程改动清单（真要实施时的最小集合）
1. 新增 `jifenWatch Watch App/Scoreboard/WatchBasketballScoreView.swift`（复用 `ScoreCore` 的 `BasketballMatchReducer` / `BasketballMatchState` 与现有菜单、确认、结束浮层和手势组件）；
2. 在 `WatchHomeItem`、`WatchScoreboardRoute`、`WatchResumeSession`、`WatchRootView` 接入本机篮球路径（清理过时注释）；
3. 在 `jifen/Core/Link/WatchLinkMenuSupport.swift` 的 `hasNoSetLayer` 补齐 `.basketball` / `.threeBasketball`，确保手表独立记录回传手机时无多余局分字段；
4. 补齐 Watch 端 41mm / 45mm UI 回归测试及记录回传单测。
