## 实际网络联调

使用一次性数据库 `jifenqi_codex_group_cross_20261001` 和 loopback API。iOS 使用从已有 iPhone 模拟器复制的独立测试设备；原设备未重置。HOS 使用已有模拟器 `127.0.0.1:5557`，安装时保留 App 数据，API 域名对应缓存与上传隔离。服务端联调入口为 `api-server/scripts/group-cross-app-server.ts`，不启用生产任务。

1. iOS 正常登录、创建“双端联调小组”，HOS 输入小组号预览后申请，iOS 成员页审批；两端刷新显示同一组的两位成员。
2. HOS 自由计分显式选择 A = iOS 账号、B = HOS 账号，原生规则设为目标 3 分、打满 2 局、封顶 15、赢两分。服务端冻结规则与席位。首次零分草稿强退后从首页续打成功。
3. 停止本地 API，完成两局：A 胜 3:0、B 胜 3:1。途中自动换边，成员身份不变；本地保存 1:1 平局，离线时数据库没有结果。恢复 API、重新启动后队列上传一次，iOS 确认后两位成员均增加一场平局。
4. HOS 补记 2:0，iOS 确认；规则、成员席位、比分事实均可读取。
5. 普通 HOS 成员创建“联调活动”，两端分别报名。HOS 从报名者明确选择参赛席位，联网开局，自定义目标 3 分、1 局制，完成 A 胜 3:0；活动变为完成，iOS 确认结果。
6. 多次强退 / 重启 HOS 后，数据库仍只有两条现场计分结果和一条补记，没有重复上传；活动仅关联一场比赛。
7. HOS 创建“鸿蒙扫码联调组”并展示实际二维码，导入 iOS 系统照片库，正常 PhotosPicker 选择 → 识别 → 预览 → 点击加入 → 等待审批；HOS 成员页审批成功，两端账号在第二组均为有效成员。

最终 [数据库 / API 事实](artifacts/2026-10-01/cross-app/backend-facts.json)：两组各两位有效成员；三条结果全部已确认，其中一条 `draw`、`winnerSide: null`；一个活动完成、两位报名者；单打排行 iOS 2 胜 1 平，HOS 0 胜 2 负 1 平，两人均出场 3 次，未满五场不显示胜率。

HOS 原有个人记录不保存逐局小分，本次上传按契约保留局分和规则，不补造小分；两端详情显示“未录入每局比分”。断网采用停止本地 API 的方式验证持久化和恢复上传，不计作飞行模式 / 系统网络回调验证。联调服务器只挂载必要路由，个人数据同步请求的 404 属于该隔离环境，不作为生产接口缺陷。
