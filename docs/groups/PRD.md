## 1. 一句话与目标

**让一帮固定球友，长期把约球、计分和战绩记在同一个地方。**

| 目标 | 成功判据 |
|---|---|
| 加入零门槛 | 新用户拿到一个 8 位数字，30 秒内进到小组 |
| 打完就留痕 | 现场完赛或赛后补记，30 秒内留下可查的比赛结果 |
| 战绩可信 | 榜单只统计已确认结果，每一行都能点回具体比赛 |
| 不伤现有体验 | 个人计分、约球、续打、通知、5 Tab 全部零回归 |

**不做什么（明确排除）**：公开发现与推荐、俱乐部、组内聊天、收费门槛、赛事导出、手表端小组管理。

## 2. 目标用户与核心场景

| 角色 | 是谁 | 最想要什么 | 最怕什么 |
|---|---|---|---|
| 组主 | 张罗局的人 | 少发微信、少重复解释，名单和比分自动攒下来 | 组被人乱加、比分被改乱 |
| 活跃成员 | 每周都来的球友 | 我的胜负别丢，双打换搭档也算我打过 | 记错对手、战绩算在别人头上 |
| 临时球友 | 没装 App 的朋友 | 今天能上场、能被记进比赛 | 被当成"数据"随便改名删除 |
| 边缘成员 | 偶尔来 | 打开就知道这周约在哪、还有没有名额 | 被拉进一堆无关通知 |

**核心场景（首批必须跑通）**

1. 老杨建了"周六羽毛球"，把小组号发到微信群，5 个人自己进来。
2. 周五约一场：时间、场地、上限 8 人，成员自己报名，报名截止前可退。
3. 周六现场开打：从约球进入计分，选实际对阵，打完自动出结果，对方确认后上榜。
4. 忘了开计分：晚上在家补记 2:1，想得起小分就展开填，想不起也不影响入账。
5. 月底看榜：谁胜场最多、谁双打净胜局领先，点进去能看到每一场的来源。

## 3. 范围分层

| 阶段 | 内容 | 准入条件 |
|---|---|---|
| **Phase 1（本 PRD 全部范围）** | 小组、加入、成员、约球报名、自由计分、补记、结果确认、战绩榜、设置 | 本文与 API 契约评审通过 |
| Phase 2 | 轮转活动（签到、场地分配、主控租约） | 轮转算法与离线策略专项评审 |
| Phase 3 | 联赛 / 赛季榜 | 规则版本、赛程、结果修正评审 |
| 暂不排期 | 球类等"平局型"项目的战绩榜 | 需先定义"平"的统计口径（见 §4.3） |

## 4. 项目范围与按项目定制

### 4.1 为什么按"形状"分档，而不是按运动个数排期

现有 iOS 计分端有 34 个 GameType。决定小组能不能承载战绩的，不是运动名称，而是**一场比赛的结果长什么形状**：

| 档 | 结果形状 | 代表项目 | 小组战绩能力 |
|---|---|---|---|
| **A** | 两方 + 局分 + 每局比分，必有胜方 | 羽毛球、乒乓球、网球、匹克球、毽球、壁球、沙滩排球、padel、软网、桌上足球、斯诺克、黑八 | **完整**：胜负场次、胜率、胜局/负局/净胜局 |
| **B** | 两方 + 单一总分，**可能平局** | 篮球、足球、排球、拳击 | 降级：比赛日志 + 胜/平/负积分表，不进胜率榜 |
| **C** | N 人混战，无稳定"两方" | 九球追分、斗地主、UNO、多计分 | 不提供战绩 tab |
| **D** | 单人训练 / 分值高者胜属推断 | 投篮训练、简易计分 | 不算竞技战绩 |

**关键事实**：A 档项目在代码里共用同一批内核（`rally` / `tennis`），记录模型 `RecordSetResult.scores: [Int]` 本身是通用的——羽毛球存 `21,18`，网球存 `6,4`，语义由规则版本决定。所以**多支持一个 A 档项目的边际成本接近零**，分批省不下工作量，只会多出一套"支持到哪了"的口径。

### 4.2 Phase 1 首批项目

**羽毛球、乒乓球、网球、匹克球**，各含单打与双打。

- 创建小组时选定项目，**创建后不可更改**（成员、赛程、战绩全部绑在一个项目上，混项目会让榜单失去意义）。
- 一个用户可加入多个小组，各项目各一组；不做"综合小组"。
- 其余 A 档项目（毽球、壁球、padel、斯诺克等）走能力目录逐个放开，不改产品结构。
- B/C/D 档项目**可以建组、约球、计分**，但战绩 tab 按 §4.3 降级或不显示——这条要在 UI 上说清楚，不能默默少一块。

### 4.3 按项目 tailor 的三个落点（tab 结构不分叉）

顶部四个页签**固定为「概览 / 活动 / 战绩 / 成员」**，不因项目增删。理由：跨端只收口一套信息架构，用户换组不用重新学；差异放在内容里足够表达。

| 定制点 | 羽毛球 | 乒乓球 | 匹克球 | 网球 | 篮球（B 档示意） |
|---|---|---|---|---|---|
| 局制术语 | 局 / 得分 | 局 / 得分 | 局 / 得分 | **盘 / 局分** | 节 / 得分 |
| 可选局制 | 三局两胜、五局三胜、一局定 | 同左 | 同左 | 三盘两胜 | 不分 |
| 每局合法比分 | 21 分制、2 分差、30 封顶 | 11 分制、2 分差 | 11 分制、2 分差、15 封顶 | 6 局制 + 抢七（**校验复杂，见下**） | 不适用 |
| 战绩 tab | 单/双打榜 | 单/双打榜 | 单/双打榜 | 单/双打榜 | 比赛日志 + 胜/平/负积分表 |
| 席位 | 单打 2 / 双打 4 | 同 | 同 | 同 | 队伍制，Phase 1 不支持 |

**网球补记是本批最大的不确定项**：网球的"每盘局分"涉及抢七、盘分与局分两套口径，原型只做了 `6 局 / 7 局` 的简化校验。建议 Phase 1 网球**只必填整场盘分（如 2:1），每盘局分先不强制**，等规则校验器补齐再放开明细。此项列入 §13 待拍板。

### 4.4 项目能力目录（实现约束）

项目清单、局制选项、每局校验器、席位数量一律由**服务端能力目录**下发，客户端不写死。理由：放开新项目不该发版；各端（iOS / Android / HarmonyOS / 小程序）必须拿到同一份口径。

## 5. 信息架构与导航

```
首页
└── 横向「我的小组」入口（位于现有"我的球局"之前）
        ├── 有小组 → 我的小组列表 → 小组详情（概览/活动/战绩/成员）
        └── 无小组 → 小组空状态（介绍 + 创建 / 加入）

底部标签：首页 · 记录 · 计分 · 计时 · 我的   （不新增第六个 Tab）
```

- 入口摘要一行：组名 + 成员数，或"和常一起玩的朋友，建立小组"。
- 首页**不**展开多个小组列表，不替换、不合并现有约球版块。
- 导航沿用各 Tab 自己的栈，小组内部页面全部 push 在首页栈上，不套第二层导航栈。

## 6. 功能需求

每条含：期望、规则、边界。验收标准统一见 §12。

### FR-01 首页横向入口

- 位置：现有"我的球局"版块之前；iPhone 与 iPad 同规则。
- 点击进入小组列表；接口失败时入口显示占位与重试，**不阻塞首页其它区块加载**。
- 未登录可点进列表看介绍，创建/加入时走既有登录恢复。

### FR-02 小组空状态

- 触发：**成功获取列表且确认为空**。加载中、请求失败、未登录**不得**伪装成空状态。
- 内容：居中线性图标 + 标题「还没有小组」+ 介绍「把常一起玩的朋友聚在这里，约一场、记比分，一起看战绩。」+ 三条能力说明（约好每一次活动 / 记录每一场比赛 / 积累共同战绩）+ 创建（主）与加入（次）两个入口，次按钮下提示"已有朋友的小组？输入小组号或扫码加入"。
- 离线且有缓存：显示缓存列表；确认为空的离线态保留介绍但创建/加入置灰并说明需联网。
- 待审批不算已加入，也不能停在空状态误导用户重建：**首页横条摘要与列表/空状态顶部都要显示"加入申请待审批 · 组名 + 小组号"卡片**，提供"刷新审批状态"与"撤回申请"；撤回后卡片消失并允许再次申请。列表接口对非成员也返回待审摘要（`GET /groups` 的 `pendingJoinRequests` 或 `GET /groups/join-requests/mine`），否则申请提交后就再也找不回来。

### FR-03 创建小组

| 字段 | 规则 |
|---|---|
| 小组名称 | 2–24 字（按 Unicode 标量计），必填，允许重名 |
| 固定项目 | 羽毛球 / 乒乓球 / 网球 / 匹克球，默认羽毛球；**创建后不可改** |
| 小组简介 | 选填，≤200 字，可留空、可后改（见 FR-07） |
| 加入方式 | 仅「需要审批（默认推荐）」或「允许直接加入」两种；**创建时不提供"关闭加入"**——还没有成员时关闭没有意义 |

- 创建成功：创建者自动成为唯一组主 + 首位账号成员，直接跳进小组详情。
- 成功后第一优先引导是**分享小组号/二维码**，不是添加临时成员。
- 服务端原子建组并分配小组号；客户端不得自行生成号码。
- 边界：成员不足时"立即计分/补记"要给出明确引导（邀请朋友或添加临时成员），不能只弹"需要 2 位成员"的死路提示。

### FR-04 小组号与二维码加入

**统一为两种入口，指向同一个小组，不再有第三套邀请码。**

| 方式 | 流程 |
|---|---|
| 小组号 | 输入 8 位纯数字 → 查找 → 预览卡片 → 加入/申请 |
| 二维码 | 扫一扫 / 从相册识别 → 解析出同一小组号 → 预览卡片 → 加入/申请 |

- 小组号：8 位十进制、首位非零、**长期不变**；组改名、转让、归档恢复、切换加入方式都**不改号**；解散后号码不回收，旧码不会指向新组。
- 小组号是**公开查找标识，不是凭证**：知道号码不等于能看到成员名单、地点和战绩。
- 预览卡片（匿名可读，限流）只返回：组名、项目、简介、成员数、加入方式、可否加入。**不含**内部地点、完整名单、战绩。
- 查找结果状态：正常 / 小组不存在 / 已满员 / 已关闭加入 / 已归档 / 已是成员 / 申请待审批。
- 扫码：拒绝相机授权仍可手输号码；连续识别需去重；识别成功**不自动加入**，必须回到预览再点一次；二维码不能绕过审批或"关闭加入"。
- 未登录：点加入才登录，登录后恢复原号码上下文，以最新状态重新校验。
- 正式二维码编码自有域名的 HTTPS 加入链接（拟 `/groups/join?groupNo=…`），微信/落地页承接需真机验证。

### FR-05 加入方式与审批

- 三种状态：`直接加入` / `需要审批` / `关闭加入`；后两者的开关只在**创建后的设置**里，且**仅组主可改**。
- 关闭加入：暂停新成员加入与待审通过，不解散、不移除成员、不影响已有成员活动和计分；可随时重新开放。
- 审批：组主与管理员可批准/拒绝；同一账号最多一条待审；申请**不占名额**；批准时才校验容量并原子占位。
- 撤回：申请人随时可撤回自己的待审请求；该操作按**请求 ID** 定位，不能要求非成员提供内部小组 ID（预览接口不下发它）。撤回后保留历史，重新申请受冷却/限流约束。
- 从"需要审批"切到"直接加入"**不自动**把待审用户拉进来，需本人再点或管理员批准；加入成功后旧的待审申请自动收口，不留悬挂。
- 被移除且标记禁止重返的成员，不能凭同一小组号自动加回，须管理员解除限制。
- 建议默认成员上限 30、硬上限 50，临时成员同样占名额；数值由服务端下发。

### FR-06 成员与角色

- 角色 `组主 / 管理员 / 成员` 与身份 `账号 / 临时` **两条正交轴**。
- 临时成员：未注册球友的参赛占位，可添加、改名、停用；**无登录权限，不能担任组主/管理员，没有结果确认入口**。
- 移除采用软删除；历史比赛继续显示当时的姓名快照，成员后续改名或退组不改动旧记录。
- 组主唯一；转让要求目标是有效账号成员且非自己，转让后原组主降为普通成员。组主不能直接退出，必须先转让。
- 归档：只读，不删除成员/比赛/历史；组主可恢复。
- 退出或移除：立即失去访问权、取消未开始活动的报名；本机个人记录保留。

### FR-07 小组简介

- 定位：回答"这是个什么组、适不适合我"，例如"周末羽毛球爱好者，新手友好，以双打为主，费用 AA"。
- 创建时选填，≤200 字；组主与管理员可改、可清空；普通成员只读。
- 展示位：小组详情概览、加入预览卡片。较长时默认两行截断 + "展开全文"。
- **不做组公告**：临时通知（停赛、改场地）放在活动详情里，避免与活动信息重复维护。确有全组通知需求时再单独评审一条可选置顶公告。
- 边界：简介是用户自填内容，需过内容审核与举报；与空状态里那句产品功能介绍是两回事，不可混用文案。

### FR-08 约球与报名

- 字段：活动名称、开始时间、地点、人数上限、（可选）备注；双打时长等默认值由项目模板给。
- 状态：`报名中 → 进行中 → 已完成`，开始前可 `已取消`；"已满"是派生显示，不是独立状态。
- 报名：成员自助报名/退报；管理员可代临时成员报名；**截止后、超容量、非成员、已归档一律服务端拒绝**，客户端不得演"本机成功、稍后再说"。
- 编辑：带版本号；下调容量不得低于有效报名数；开始后锁定赛制与席位。
- 取消：二次确认，填写原因，通知已报名成员。
- Phase 1 口径：**一次约球对应一场正式比赛**。容量可大于席位数，开赛前选定实际对阵；同一活动只允许一个未作废的比赛。
- 提醒：小组活动提醒与本机个人约球提醒分属不同命名空间，互不覆盖。

### FR-09 立即计分与席位

- 入口：概览「立即计分」，或从活动详情开赛。
- 席位：单打 2 人（A/B 各 1）、双打 4 人（A/B 各 2），必须来自本组有效成员，同一个人不能同时出现在双方。
- 席位身份在开局时快照，**换边、续打、崩溃恢复都不能丢失成员归属**；服务端 side A/B 映射到稳定队伍标识，不按屏幕左右猜。
- 复用现有计分板与规则引擎，小组只负责"带上下文进入"和"带结果出来"，不重写计分逻辑。
- 沿用全局单活跃会话保护；本机启动失败要补偿释放活动占用，超时不自动重开。

### FR-10 补记比赛

- 交互：**整场局分必填**（如 2:1），**每局比分选填**可展开。
- 局分按所选局制校验：三局两胜允许 2:0 / 2:1 / 0:2 / 1:2；未完赛、平局、负数不得作为完赛补记。
- 每局比分**整组可选**：全部留空表示明细缺失；一旦填了任何一格，要求补全所有已赛局，且局数必须等于 A 胜局 + B 胜局。
- 逐局比分先过**该项目的合法终局校验**，再按顺序推导胜局，与整场局分三方核对；任一方已达获胜局数后不得再填后续局。
- 未录入的小分**不按 0 统计**：仍统计场次、胜负、胜局/负局/净胜局；不参与净胜小分等需要明细的指标。
- 修改局分导致局数变化时保留草稿并确认是否移除多余局，禁止静默丢用户输入。
- 弃权/退赛/超时裁定是独立结果类型，Phase 1 不通过伪造 2:0 或 21:0 支持。

### FR-11 结果状态与确认

```
本机：已保存 → 待提交 → 已提交
服务端：待确认 → 已确认 / 有争议 ；已确认 →（更正）→ 待确认 ；→ 已作废
```

- 正常计分与手工补记**都先进入待确认**，不自动入榜。
- 谁能确认：对方参赛席位中的非提交者，或组主/管理员（管理员确认强制留审计）。**同一账号不能自证双方**。
- 临时成员无确认入口；若对阵双方都是临时成员，由管理员核对。
- 更正走新版本审核，不覆盖旧事实；争议期间是否暂停统计需固定口径（设计建议：更正审核期继续统计旧确认版本，裁定成功原子切换；正式争议触发暂停）。
- 重复提交：同一比赛同一内容返回原结果；同一比赛不同内容判为结果冲突，要求走更正。疑似"同时段同席位同比分"只能提示，不能自动去重真实发生的复赛。
- 删除本机记录、改备注**不影响**已共享结果；撤销必须走作废/更正。
- 小组共享结果**不含**个人备注、语音、音频路径、定位历史和完整状态快照。

### FR-12 战绩与排行榜

- 榜单**只汇总当前赛制的已确认有效结果**；单打、双打分开，不混排。
- 双打：每名参与者各记一次出场/胜场（搭档不计胜场）。
- 排序：胜场降序 → 胜率降序 → 参赛场次降序 → 稳定次序（成员 ID）保证分页不跳。
- 胜率**满 5 场才显示**，未满显示"场次不足"，不用小数误导。
- 时间过滤按完成时间；作废与重复结果不计。
- 每一行可下钻到具体比赛列表，再点进比赛详情（含局分、每局明细、来源、提交人、确认人）。
- 榜单是**派生数据**，可重算；客户端不做永久累计。

### FR-13 设置与权限

| 动作 | 组主 | 管理员 | 普通成员 |
|---|---|---|---|
| 浏览、报名、计分/提交 | ✓ | ✓ | ✓ |
| 分享小组号 / 二维码 | ✓ | ✓ | ✓ |
| 修改小组简介 | ✓ | ✓ | — |
| 创建/修改/取消活动 | ✓ | ✓ | 自己创建且未开始的 |
| 审批加入、临时成员认领 | ✓ | ✓ | — |
| 添加/改名/停用临时成员 | ✓ | ✓ | — |
| 修改加入方式（含关闭） | ✓ | — | — |
| 任命/撤销管理员、转让、归档、解散 | ✓ | — | — |
| 确认结果 | ✓（留审计） | ✓（留审计） | 对方席位且非提交者 |
| 作废/裁定冲突 | ✓（必填原因） | ✓（必填原因） | 只能发起争议 |

权限一律服务端复核，客户端隐藏按钮只是体验，不是安全边界。

### FR-14 临时成员认领

- 双确认：账号用户先认领，管理员再核对；**不能仅凭公开小组号认领任意成员的历史**。
- 未在组内 → 临时成员转为账号成员，保留成员 ID 与历史；已在组内 → 临时成员标记为已合并并指向已有成员，**绝不按姓名自动合并**。
- 历史快照不改写；统计按合并后的规范成员 ID 解析；若合并导致同一账号落在一场比赛双方席位，标记待人工核验、暂不入榜。

### FR-15 离线与同步

- 离线可用：浏览缓存的小组/活动/战绩，**自由比赛**可本机继续或新开并保存。
- 离线不可用：创建小组、加入、报名、修改成员与设置、占用约球比赛（未拿到服务端比赛 ID 时）、发布轮转。
- 恢复联网：手动或前台自动触发提交；失败区分可重试 / 需登录 / 永久拒绝 / 冲突，**永久拒绝必须可见并停止自动重试**。
- 崩溃安全：本机正式记录落盘成功但提交任务未建立之间崩溃，恢复时要补建任务，不丢共享结果；已提交但回执未落盘时重试沿用原幂等键，不重复入榜、不串账号。
- 退出登录：清可浏览缓存与提醒，未提交队列隔离保存，另一账号不能读取或代发。

### FR-16 通知

- 触发点：新成员申请待审、申请通过/拒绝、活动创建/变更/取消、结果待确认、结果被确认/更正/作废、被任命或撤销管理员、被移出小组、所有权转让。
- 推送只是加速手段，**不作为正确性依赖**；用户可关。本地提醒与个人约球提醒互不覆盖。

### FR-17 埋点与可观测

只记操作与结果，不记成绩正文、小组号明文、成员姓名。建议事件：

`group_home_entry_view` · `group_create_submit` · `group_lookup_submit` · `group_join_submit` · `group_qr_scan_result` · `group_activity_create` · `group_activity_register` · `group_game_start` · `group_result_submit` · `group_result_confirm` · `group_result_manual` · `group_ranking_view`

**合规前置**：本产品规划中的中国区广场含 UGC，小组名称/简介/成员昵称均为**用户生成内容**，SDK 与合规建议一律按"UGC App"口径评估，不沿用无 UGC 结论。

### FR-18 本地化与无障碍

- 全部文案走现有多语言机制；本产品已支持十余种语言，新增 key 需同批补齐，不留半翻译。
- 中文口径：术语统一用「小组 / 小组号 / 简介 / 局分 / 盘分」，不与"队伍""俱乐部""邀请码"混用。
- 深浅色、Dynamic Type、iPad 宽度沿用现有 Theme 规则；二维码图片深色模式下不反色，保留白色静区。
- 表单错误就地提示，不依赖颜色单独表意。

## 8. 数据与统计口径

| 指标 | 定义 | 排除 |
|---|---|---|
| 已确认比赛数 | 状态为已确认且未作废的结果数 | 待确认、争议、作废、草稿 |
| 出场场次 | 出现在有效结果参赛席位中的次数 | 非本组、跨赛制 |
| 胜场 | 有效结果中该成员所在方为胜方 | 平局（B 档另计"平"） |
| 胜率 | 胜场 / 出场场次 | 满 5 场才显示 |
| 胜局 / 负局 / 净胜局 | 按整场局分累计 | 无明细不影响此项 |
| 净胜小分等明细指标 | 按每局比分累计 | **仅统计有明细的场次，并返回覆盖率/总场数** |
| 近 30 天活跃 | 至少参加过一场已完成比赛 | 取消的赛程、非小组计分 |

原则：赛果的唯一权威是**已确认的结果记录**；任何展示用的汇总都必须可追溯到来源比赛并可重算，不允许存在第二份可独立修改的比分。

## 9. 跨端与合规边界

- 小组是跨端一致的产品概念，各端功能开关通过能力目录 + 最低版本协商，**不允许出现 iOS 专属群**。
- 分享链接、微信小程序路径、Universal Link 均只携带同一个固定小组号，不额外生成凭证。
- 跨端账号是否同一人，取决于已验证的身份绑定，**不由分享页或相同昵称自动合并**。
- 小组数据与实时投屏/多设备同步的房间体系完全独立；属于同一小组不等于能接管他人计分板。
- 注销账号：有其它账号成员时要求先转让；仅剩本人与临时成员时可先归档处置。保留匿名化的原始比分与审计，展示层匿名化姓名。

## 10. 上线门槛（不达标不上）

1. 加入闭环：手输、扫码、相册识别、深链四种路径回到同一预览，行为一致；二维码与小组号都不能绕过审批或关闭状态。
2. 号码稳定性：同一小组号各端定位同组；改名/转让/归档恢复不改号；解散后不回收。
3. 权限：任何越权审批、确认、移除、转让、改加入方式都被服务端拒绝。
4. 幂等与崩溃：重试、超时后重试、提交成功后崩溃，都只产生一条结果；真机杀进程覆盖"记录已落盘但未入队"和"请求成功但回执未落"两种窗口。
5. 战绩正确性：待确认不入榜；确认/作废/更正/认领后统计可追溯且可重算；同名两人不混淆；缺失小分不当 0 统计。
6. 隐私：抓包看不到个人备注、语音、音频路径、完整状态快照；按号预览不含内部地点与名单。
7. 回归：首页原有计分、约球、续打、通知、5 Tab、多语言、iPad 布局全部通过。
8. 后端迁移在 staging 验证旧客户端兼容与回滚开关后再分端灰度；本轮不部署、不提审。

## 12. 验收标准（可测）

**FR-01 入口 / FR-02 列表状态**
- 进入"我的小组"而请求未回 → 显示加载态；不得把"还不知道"画成"没有小组"。
- 请求失败且本机无缓存 → 失败页 + 重试，重试成功后回到列表；失败页文案明确"这不等于你没有小组"。
- 请求失败但有缓存 → 展示缓存列表并标注最后同步时间，创建/加入/报名等写操作禁用。
- 只有服务端确认返回空数组才进入空状态；空状态用固定版式，不用通用"暂无数据"占位。
- 申请待审批后返回：首页横条摘要显示"加入申请待审批 · 组名"，"我的小组"（含空状态）顶部显示待审批卡片与刷新/撤回；撤回后恢复普通空状态。
- 待审批期间不显示小组内部内容（成员、战绩），也不因为刷新而重复提交申请。

**FR-03 创建**
- 组主未登录时提交创建 → 走登录后回到原表单，草稿不丢。
- 在创建表单尝试提交"关闭加入" → 该选项不存在，绕过前端直接请求也返回 `422 INVALID_INITIAL_JOIN_POLICY`。
- 名称 1 字 / 25 字 → 就地提示；简介 201 字 → 就地提示；200 字整 → 通过。

**FR-04 加入**
- 输入 7 位或以 0 开头 → 提示格式；输入正确号码 → 预览卡片含组名、项目、简介、人数、加入方式，且不含地点与名单。
- 未登录点加入 → 登录后自动恢复该号码上下文并重新校验最新状态。
- 相机权限拒绝 → 仍可用手输；同一码连续扫 3 次 → 只产生一次解析。
- 组主关闭加入后，旧二维码再扫 → 显示"已关闭加入"，无法加入。

**FR-08 约球**
- 有效报名数 5 时把容量下调到 4 → 拒绝并保留原值。
- 报名截止后点击报名 → 拒绝并显示截止时间，客户端不出现"已报名"闪现。
- 同一活动两端同时开赛 → 只成功一场，另一端拿到已有比赛或冲突提示。

**FR-10 补记（羽毛球）**
- 只填 2:1 → 保存成功，详情显示"未录入每局比分"。
- 填 21:18、17:21、21:19 → 保存成功，主比分仍为 2:1。
- 合计 1:2 与整场 2:1 不一致 → 拦截并指出合计差异。
- 前两局已 2:0 还填第三局 → 拦截。
- 只填其中一格 → 提示补全或全部留空。

**FR-10 补记（跨项目）**
- 网球组补记 6:4、3:6、7:5 → 通过；填 21:18 → 提示"不是有效的终局局分，例如 6:4 或 7:5"。
- 匹克球组补记 11:6 → 通过；填 21:18 → 拒绝。
- 同一份逐局比分在不同项目下判定不同 → 证明校验来自能力目录而非客户端写死。

**FR-11 结果**
- 提交方自己点确认 → 无入口且直接请求被拒；对方席位成员确认 → 入榜。
- 已确认结果被更正 → 旧版本保留可查，统计按裁定结果原子切换。
- 同一比赛重复提交相同内容 → 返回原结果；不同内容 → 结果冲突。

**FR-12 战绩**
- 4 场已确认时胜率列显示"场次不足"，5 场时显示数值。
- 单/双打切换 → 榜单与比赛列表同步过滤，不混排。
- 点击某成员 → 只显示该成员参与且当前赛制的比赛。
- 作废一场比赛 → 该成员场次与胜场同步减少。

**FR-15 离线**
- 离线状态：自由比赛可开局并保存为待提交；约球占用与所有写操作置灰并说明原因。
- 恢复联网 → 手动同步后待提交变待确认，数量一致、不重复。

## 14. 原型已知缺口（写代码前补齐）

原型 v10 已收口两条：待审批回访入口（首页横条摘要 + 我的小组/空状态顶部卡片，含刷新与撤回）、小组列表的加载中与请求失败态（评审工具"网络与访问状态"新增两项，并有缓存提示文案）。加载/失败目前只覆盖"我的小组"列表页与页内提示条，**小组号查找结果页、结果详情页仍未画这两种态**，原生实现需按 §7 状态矩阵逐页补齐。

| 缺口 | 严重度 | 说明 |

| 多小组管理未演示 | 低 | 原型是单组模型，创建会替换当前组数据 |
| 成员排行仅胜场排序 | 低 | 未演示胜率并列、净胜局决胜与同名区分 |
| 通知中心与举报入口未画 | 低 | 契约已定义，UI 待补 |
| 账号注销与小组处置未演示 | 低 | 属上线前必查项 |
