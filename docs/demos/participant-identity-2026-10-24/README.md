# 应用昵称、旧名字与本人参赛记录

日期：2026-10-24。状态：交互方案与 HTML 演示已确认，各端与服务端已完成本地实施和验证，尚未部署。最新落地口径与验证见 [实施记录](../../implementation/participant-identity-2026-10-24.md)。

后续确认优先于早期演示：统一名称为“我的记录”；本轮不新增小组昵称；小组个人统计只读取既有权限下的正式成员已确认成绩；登录自动承接私人全库（含计时和语音），承接或账号合并超额名称转待整理，不阻断现有绑定。记录页以更多菜单中的统一筛选替代常驻分类。

## 用户已确认的方向

- 复用应用昵称，不新增独立的全局 Display Name。
- 普通 Setup 的选手列表置顶当前账号昵称，显示“我”；选择后填入昵称，同时保留本人身份。队名列表不把个人昵称当作队伍。
- 本轮不新增小组昵称字段或配置；小组使用现有正式成员账号映射与既有名称逻辑。
- 升级前大量本地比赛按旧名字批量关联本人，不要求逐场认领。
- 关联后的多个名字可以继续用于参赛，选人列表统一显示“我”；当前应用昵称排第一。
- 关联名称最多 3 个；当前应用昵称的自动置顶项不额外占用关联名额。
- 未登录也有稳定的“本机的我”：可直接选“我”参赛，也可设置一个选用名称、关联本地名字，常用名称与个人统计都可使用；登录不是前置条件。
- 登录后正常自动承接尚未归属账号的本机身份与关联。只有名额或归属冲突时再处理，不要求常规路径二次认领。
- 同一场比赛中，同一人只占一个个人参赛位置；关联到本人的其他名字在其余位置禁选，当前位置可切换自己的名字，双打等多人名单同样适用。
- 各端最终共用同一套身份、关联与统计规则。

## 建议规则

建议同一人可以关联多个旧名字，并随时补充、解除。记录者不一定是参赛人，不能用创建记录的账号直接推定其参赛身份。

### 关联数量上限

每个本人身份最多有 3 个有效关联名称，按规范化名称去重计数。当前应用昵称自动置顶的身份入口不额外占关联名额；计数以实际确认的关联映射为准，不因改昵称自动增加、删除或重新计算名称映射。

常用名称的关联分组显示 `3 / 3`。达到上限后禁选新名称；可在该组的行菜单中解除已有名称。已有名称发现新的旧记录，仍可补充，不占新名额。多选过程中动态计算最终数量，确认提交时再次检查。

从选人列表移除只是隐藏快捷入口，仍占名额；明确解除名称关联才释放名额。以后重新关联按新增处理。规则对游客本机身份、已登录账号和跨端一致。

游客归入账号时，对双方名称取规范化去重后的并集再次校验；正常直接自动承接。超过 3 个时主账号有效名称优先，多余名称保留为待整理，不占有效名额，不阻断其他私人记录同步或账号绑定。历史关联继续保留。正式跨端落地还需要服务端在同一事务中校验，防止多设备同时提交各自通过检查而突破上限。

### 名字关联的长期含义

关联包含两个部分：补齐明确范围内的旧记录，以及把这个可选名称对应到本人身份。以后从选人列表选择带“我”的任意关联名称，都保存同一个本人身份，同时保留本场所选的显示名称。不是仅能迁移一次的历史工具。

只靠名字文字碰巧相同，不自动赋予身份。手动填写的普通名称不标记“我”，可以用于真正重名的其他球友。

从常用/选人列表移除名称，只隐藏快捷入口，不撤销已有记录关联；关联管理中仍能找到并恢复该名称。当前应用昵称持续置顶，不因移除旧名而消失。

解除名称关联是另一项明确操作：停止将这个可选名称当作本人，撤销该次名称确认形成的旧记录关联；已通过稳定本人身份直接保存的新比赛仍保留，不按显示名称回溯剥离。这两种操作不能都叫“删除”。

### 入口和生命周期

关联管理长期保留在“首页 → 常用名称 → 选手名称”。已关联名称直接展开成一组，每行提供菜单；不再并列“关联名称”和“管理关联名称”两个导航入口。

首次进入尚未关联时，也保留这个分组，显示 `0 / 3`。分组内只显示一行“关联用过的名称”入口，不使用大块空态或重复解释。点击后按名称批量选择历史数据；也可以直接从下方常用选手的行菜单点击“关联为我”。完成第一项关联后，该行名称带“我”出现在同一分组中，数量变为 `1 / 3`。

登录昵称自动置顶并标“我”，无需手动关联，也不预先给用户绑定其他旧名。删除全部关联后恢复 `0 / 3` 和同一入口。未登录时不显示账号昵称，但本机关联入口依旧保留；队伍分类不显示个人关联分组。

升级后发现可处理旧记录时，展示一次可跳过的引导。跳过不失去能力；以后登录、改昵称、导入数据或发现漏掉的名字，都可以再次进入。无旧数据不展示引导。

候选来自实际历史记录中的个人名称，不是把常用名称列表当作参赛历史。候选按规范化名称分组，展示涉及场次并提供少量记录预览；用户可同时勾选多个旧名字，一次确认整批关联。

未登录时，创建本地稳定本人标识，展示为“我”。不是用名字文字或设备硬件 ID 充当身份。Setup 默认提供“我”，无需先登录或先填名字；也可以从常用选手中选择一个名称作为“我”，再补充其他关联名称，最多 3 个。

本机默认选用名称只是已关联名称的引用，不增加第三个全局 Display Name 字段。第一个确认的名称默认用于本机“我”的显示；未来可切换为其他已关联名称。没有选用名称时仍可直接用“我”。常用名称页保留本机身份入口；个人统计按同一个本地本人标识汇总。

关联完成先保存本机，提供可跳过的“登录并同步”提示，不阻挡本机使用。登录成功后将本机本人标识映射到账号，自动承接此前的本人记录、名称关联与统计，使用稳定比赛身份去重。无需再让用户逐个名字或逐场确认。名额超限的名称进入待整理，已有账号归属冲突的数据保留原归属，不能重新承接给另一账号。

只自动承接尚未归属账号的本机身份；A 账号已经拥有的数据不能因为登录 B 账号而再次迁移。退出账号、新游客身份和会话过期需区分；会话过期不得把已有账号数据重新标成可被其他账号领取的匿名数据。

### 按名字选，按明确的历史数据范围落库

历史记录部分通过名字生成这一次批量关联的候选；不在全站按相同名字搜索归属。未来部分由选中的名称条目携带本人身份，不再靠扫描名字文字猜测。

候选范围为本机无账号归属的历史数据，以及当前账号可访问并处理的私人历史数据。其他账号的私人库、其他人的已绑定身份不在范围内。私人记录中的自我标记不修改共享小组身份、排名、赛果确认权限。

一次提交至少保留：规范化旧名字、来源数据范围、实际关联的历史比赛及稳定参赛位置、操作者/本人身份、确认时间、版本与撤销状态。服务端从登录凭据确认账号身份，不信任客户端随意指定的目标账号。

用户在界面上勾选的是名字，不是逐场勾选；落库保留具体比赛与位置，便于稳定统计、处理换边、撤销和防止规则误扩散。需要使用比赛内稳定选手位置/身份，不能使用当前画面左边/右边推测历史身份。

以后新导入的旧记录，可以按已关联旧名字提示“新增 N 场可补充”，一次确认补充，仍不需要逐场确认。不要悄悄扩大先前确认过的数据范围。

### 不修改原始数据

关联不覆盖历史名称、比分、动作日志或比赛胜方，不把多个名字替换成当前昵称。

应用昵称变化不影响已有身份关联。本轮沿用既有小组名称与账号身份映射，不新增组内昵称配置。

支持解除某个旧名字对应的历史关联；保留原记录，重新计算统计。解除不删除通过 Setup“我”或已验证小组身份形成的其他关联。撤销与新增同样参与同步，旧客户端不能把已撤销关系恢复。

### 同名与统计边界

- 用户确认意味着“这批历史数据里，这个名字代表我”。不能同时承诺仅凭名字证明真实身份。
- 可选的日期、项目、来源范围只作为混用同名时的纠错方式，不作为每个人必走的步骤。
- 一场比赛同时出现多个被关联旧名，或同名出现在多个个人席位时，不能确定本人位置：保留关联说明，暂不计入个人胜负；不要求用户先逐场处理才能完成其他旧名的关联。
- 只有队名、没有个人名单的团队赛，不把队名关联成一个人。将来如支持“我参加了该队比赛”，应另设参赛标记；不能据此推导个人得分等数据。
- 手机、手表、小组回传等同一场比赛，以稳定来源比赛/会话身份去重，不能通过姓名、日期和比分相同就合并。没有可靠同场身份时不得承诺自动去重。
- 单打、双打、团队参赛及各运动分别统计。记录者、创建者、同步账号不能直接等同于参赛人。
- 年终回顾和后续 AI 分析使用明确本人身份且无冲突、去重后的记录，并保留来源和确认方式；不通过改昵称重算历史归属。

### 新比赛

新 Setup 中当前昵称与已关联的其他名称都显示“我”。选择任意一个时，写入稳定本人身份和本场显示名称；普通名字输入/未关联同名不自动等于“我”。修改该字段或替换参赛人时，必须同步维护或清除身份，不能留下名字属于他人但 ID 属于本人的状态。

当前昵称第一，已关联名称随后，其余普通名称在后。名称文字规范化去重，同一人的多个名称不拆成多个人。

任意个人参赛位置选中本人后，其他位置的全部本人名称禁选，直接展示“你已在左侧参赛”等必要提示，不在每个禁用行重复解释。在同一位置切换本人的多个名称允许；移动参赛位置前先清除原位置，不静默复制或自动移动。

单打双方、双打双方的全部队员、以及其他多人模式统一按稳定人员身份查重；不能只校验名字文字，或只检查两个对手之间。提交前再次检查所有当前生效的参赛位置。队伍名称不套用个人身份逻辑。

历史批量关联仍仅作用于确认过的旧数据范围；后导入记录可按名称批量补充，避免未经确认扩张历史数据范围。

### 页面与文案

删除“我的参赛记录”页中“名字怎么使用”整个 section，并把名称管理彻底移出参赛记录页。正式入口位置细化如下：

| 页面路径 | 显示内容和操作 |
| --- | --- |
| 首页 → 常用数据 → 常用名称 → 选手名称 | 当前昵称单列；“已关联本人 3/3”直接展开三个名称与行菜单；普通选手名单随后 |
| 已关联本人分组 | 每行显示名称和“我”；行菜单可补充旧记录、移出快捷选择、解除关联。分组内有“从历史记录关联”入口 |
| 普通常用选手名称的行菜单 | “关联为我”，满额时禁用；明确将现有名称与本人对应，而不必先进入历史扫描页 |
| 常用名称 → 队伍名称 | 只显示队名，不显示个人关联分组和“关联为我”操作 |
| 记录 → 我的记录 | 根页正文第一项长期保留个人入口；原分类收入更多菜单的统一筛选；个人页是二级页面、隐藏主 Tab bar，只看本人记录与统计 |
| 我的参赛无记录时 | 可提供“去常用名称关联本人”空态操作；有记录后不重复摆管理入口 |
| Setup 选人 → 管理常用名称 | 常用名称的另一情境入口；修改完成返回原参赛位置，保留已选名单 |
| 我的 → 个人资料 | 修改应用昵称 |
| 首页 → 本组 → 我的设置 → 本组昵称 | 只修改本组昵称 |

常用名称页只有一份关联分组，不另建一份“我的关联名称”管理数据。通过历史批量确认或普通名单关联后，都回到同一展开分组。

选人和关联列表以名字、“我”、场次数表达状态。移除重复的第二行用途说明、日期和常驻规则段落，完整规则放在标题旁的问号中。重复身份禁选、本机保存、自动同步的异常、解除的影响等直接影响当前操作的信息仍在当场显示。

“关联历史名称”页列出全部候选，始终展开，不设“更多 / 收起”；列表区域上下滚动。标题、数量信息与底部“关联到我”操作固定，滚动不带走按钮，末行不会被按钮覆盖。选中名称后保留列表滚动位置。

Tab bar 只出现在首页、记录、我的等主入口。常用名称、关联历史名称、个人参赛详情、个人资料、小组详情等二级页面不显示；返回主入口后恢复。候选记录布局中的“我的参赛”若为独立详情页也隐藏，若只是主记录页的原地视图切换则保留。

标题沿用各端现有样式：原型中 iOS 居中、Android 左对齐；左对齐的二级页在返回箭头后放标题。主记录页的分类位置分别评估左上入口和右侧筛选，不强行把 Android 标题改成居中。固定手机高度仅用于原型演示滚动，原生实现应按实际窗口可用高度和安全区布局。

### 小组

已关联账号的小组成员及其记录，沿用现有成员/账号对应，不再走旧名字批量关联。

旧临时成员要与正式账号合并属于另一项组内身份操作，需要独立的权限、双方/管理员确认及审计方案；不允许通过私人库里勾选一个名字，改变共享小组的成员身份或历史赛果权限。本轮演示不引入这项额外功能。

## 现有代码证据与实施注意

- iOS `AppUser` 已有应用姓名/昵称及展示取值，个人资料有改昵称流程；无需增加第三个全局名字字段。
- 小组 `GroupMember` 已有 `accountId` / `displayName` 与历史成员身份映射；服务端普通账号成员的展示仍有优先读取 `user.name` 的代码，正式成员不能直接用现有临时成员改名接口。因此“组内昵称”并非只补一个客户端输入框，需要统一服务端取值、权限、审核和缓存刷新。
- iOS 普通旧记录有比赛内名称/稳定位置等信息，但没有通用的“这个参赛人就是某账号”关系。同步 mutation 的 actor 是同步操作者，也不能拿来认定本人参赛。
- 新增独立的参赛身份关联层，避免重写所有旧比分与回放数据。实际数据协议还需覆盖其他客户端、同步服务、历史记录 ID 与来源 ID。

## 跨端实施范围

| 部分 | 统一要求 |
| --- | --- |
| 服务端/同步 | 关联数据、本人身份、范围、幂等、版本、撤销、账号隔离及可靠同场去重；小组昵称覆盖与跟随规则 |
| iOS / Android / Android Google / HarmonyOS | 本人置顶、名字批量关联、永久管理入口、升级引导、游客归入账号、统计口径 |
| 网页 / 微信小程序 | 对具备登录、Setup 或历史记录能力的界面应用同一规则；不能从其他平台读到的名字重新猜身份 |
| 手表及手机联动 | 有选人能力时传递本人身份；历史记录保留原始来源 ID；无管理界面时通过手机管理关联 |

HTML 中的平台选项只示意同一套交互在不同外观中的展示，不代表各端已实现或通过编译。后续落地需分别核对各仓库实际能力，不应把多个手表产品假定为共享一个账号/记录体系。

## 演示内容

名称流程：首页 → 常用名称 → 选手名称 → 直接查看已关联分组；可从普通名称菜单“关联为我”，也可从历史记录按名称批量补充，完成后回到同一分组。

记录流程：底部记录 → 我的参赛 → 本人统计与具体比赛；不在此页混排名称管理。

附带状态：未登录直接选“我”、选择本机使用的名称、最多关联 3 个名字、登录后自动承接、换账号隔离、后来导入旧记录后的补充关联、改应用昵称、设置本组昵称、关联名称均显示“我”、跨位置身份禁选、选人条目移除与关联解除分开。

本轮默认从未登录的“关联历史名称”二级页开始：全部候选可滚动，按钮固定底部，无 Tab bar。没有预置关联，初始为 `0 / 3`。返回可查看常用名称中的本机“我”和首次关联入口；再次返回首页才出现主导航。预览设置可切换 Android 左对齐标题或其他页面。计时只保留既有导航位置，不扩展本次无关功能。

记录页最新布局见 `record-unified-filter/README.md` 与其交互源：类型并入“更多 → 筛选”，与时间、项目共用同一入口；正文保留“我的参赛”。此前 `record-tab-options/` 的四个布局作为探索存档。本目录主交互源仍是本人身份流程快照，记录页最终布局以 `record-unified-filter/` 为准。

## 本轮验证

- 浏览器实点：勾选三个旧名字，一次确认，6 场旧记录按比赛去重，其中 1 场身份重叠不计入个人胜负；统计与预期一致。
- 早期版本曾验证登录后显式确认；本轮已按新决策改为正常自动承接，旧交互不再适用。
- 检查了正常宽度深色、320px 窄宽浅色的主流程与确认弹窗。
- 使用演示脚本的纯逻辑验证了重复提交、昵称变化、解除、后来导入后的补充、账号隔离、游客归入账号，以及原始记录未被改写。
- 最终脚本语法检查通过，仓库交互源与对话内预览源一致。
- 本轮更新实点验证：所有关联名称显示“我”；当前位置切换别名保留身份；双打同队其他位置也禁选全部本人名称；精简页面中不再出现“名字怎么使用”section。
- 本轮更新纯逻辑验证：拒绝把同一个人以不同名称放入不同位置；从选人列表移除不改变旧记录统计；解除名称关联会清除尚未开始比赛的相应别名身份；提交名单前再次检查身份唯一性。
- 数量限制：最多 3 个名称，确认提交及游客归入账号时再次校验；隐藏不释放名额，补充已有名称的记录不占新名额。
- 位置细化实点验证：首页进入常用名称；选手页直接展开 3/3 分组；队伍页隐藏个人关联；普通名称菜单满额禁选；解除 YY 后变为 2/3，再经普通名称菜单重新关联，回到原分组。
- 位置细化实点验证：记录保留全部/计分/计时分类；我的参赛只显示统计和比赛；详情行保留当时名称并正确标记“我”。
- 上下文返回与名额边界通过纯逻辑检查；Setup 进入名称管理后返回，原目标位置与选中名称保留。
- 首次使用实点验证：初始无预置关联，分组为 0/3 且保留紧凑入口；点击入口选择“杨扬”，确认后回到同一分组，显示 1/3 和“我”。纯逻辑同时验证了解除全部后恢复 0/3、队伍分类仍隐藏个人分组、当前昵称无需额外关联。
- 本机身份纯逻辑验证：未关联任何名称时已可选“我”；选中后其他位置禁选同一个本人身份。关联名字后本机统计生效，首次关联名成为默认选用名称；登录自动承接关联、本人统计与未开赛名单，原始历史名称与比分不改写。

- 历史列表浏览器检查：7 个候选始终展开。列表滚动位置由 0 变为 97 后，底部按钮位置仍为 top 635 / bottom 681；最后一项可见、可选，按钮不随列表滚动。
- 层级与平台检查：关联历史名称、常用名称等二级页隐藏 Tab bar，返回首页恢复。Android 标题实测左对齐，7 个候选完整显示，底部操作区可见；iOS 保留居中标题。记录布局候选中的二级“我的参赛”详情同样隐藏 Tab bar。
