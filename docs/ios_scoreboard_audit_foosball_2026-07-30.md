## 2. Setup 流程逐项对比

| Setup 项 | 1V1 | 2V2 | 默认值 / 规则 |
|----------|:---:|:---:|----------------|
| 单双打选择 | ✅ | ✅ | 默认 2V2 |
| 名称输入 | 双方各 1 人 | 四名球员独立输入 | 1V1：选手A/B；2V2：红方A/红方B、蓝方A/蓝方B |
| 完成方式 | ✅ | ✅ | 经典（先胜）/打满 |
| 局数 | ✅ | ✅ | 默认 3；经典仅允许 1-99 奇数，打满允许 1-99 |
| 每局分数 | ✅ | ✅ | 默认 5；预设 5/7/8；自定义 1-99 |
| 决胜局净胜 2 分 | ✅ | ✅ | 默认关闭；只作用于最后一局 |
| 决胜局封顶分 | ✅ | ✅ | 无/8/10/自定义 1-99；只在净胜 2 分开启后显示 |
| 发球方 | ❌ | ❌ | 桌上足球没有发球轮换模型 |
| 自动换边 | ❌ Setup 不提供 | ❌ Setup 不提供 | 比赛中可从菜单手动换边 |

### Setup 映射结论

- `isSingles` 正确决定 `.foosball` / `.foosballDoubles`。
- `maxSets`、`matchCompletionMode`、`pointsPerSet`、`winByTwo`、`scoreCap` 均能进入 `RallyRuleSet`。
- 2V2 的四名球员不是只拼成两个显示字符串：Session 中保留四个稳定 participant ID，顺序为左上、右上、左下、右下。
- 已修复封顶分校验：封顶分必须位于“每局目标分...99”，不能再构造“8 分制、1 分封顶”一类错误规则。

## 3. 页面布局与交互

### 3.1 1V1

| 维度 | 描述 |
|------|------|
| **布局** | 左右 50/50 分屏，使用实时 `GeometryReader` 尺寸 |
| **显示内容** | 选手名 → 当前局分 → 已胜局数 |
| **发球指示** | ❌ 隐藏，符合桌上足球规则 |
| **关键分标识** | ✅ `KeyPointResolver.rally` |
| **计分** | 单击半区 +1 |
| **减分** | 下滑 -1，最低为 0 |
| **撤销** | 左滑撤销，也可从菜单撤销 |
| **编辑模式** | 双方名称、当前局分、已胜局数均可编辑；加分受结算边界保护 |
| **换边** | ✅ 只改变屏幕位置，不交换队伍身份和历史 |

### 3.2 2V2

| 维度 | 描述 |
|------|------|
| **比赛态布局** | 仍为左右两块队伍面板，显示 `红方A/红方B` 与 `蓝方A/蓝方B` |
| **编辑态布局** | 每侧拆成上下两个球员输入框，四人可独立改名 |
| **计分规则** | 与 1V1 相同，按队伍累计 |
| **发球轮换** | ❌ 不适用；`RallyDoublesState.foosball` 明确不做轮换 |
| **换边后身份** | ✅ 四名球员仍归属于原队，只改变左右屏幕位置 |
| **Draft / 再来一场** | ✅ 四人身份和单双打类型均保留 |

## 7. 手机、iPad、手表与语音

| 平台 / 能力 | 结论 |
|-------------|------|
| iPhone | 横屏计分，布局正常 |
| iPad | 使用容器实测尺寸；按“强制 iPad 横屏”偏好决定锁定或解锁方向，未使用 `UIScreen.main.bounds` |
| Apple Watch | 当前功能开关明确排除桌上足球，Setup 不显示“在手表开始”；属于未规划能力，不是坏链路 |
| 语音播报 | `VoiceAnnouncementSupport` 明确不包含桌上足球；菜单不显示开关，属于未支持能力 |
| Android / HarmonyOS | 核心赛制和 2V2 身份模型一致；部分手势、菜单和跨端同步能力不同，属于平台能力差异 |

## 9. 验证结果

- App 定向测试：3 项通过（Setup 全字段映射、非法封顶分、单局结果展示）。
- ScoreCore 桌上足球测试：4 项通过（默认规则、决胜局规则、四人身份、双打改名）。
- Session / Record 回归：2 项通过（新比赛新 UUID 且保留配置、单双打记录恢复）。
- `xcodebuild` 使用 `.xcworkspace` 完成 App 与测试目标编译。

## 10. 结论

桌上足球的主体架构、1V1/2V2 规则、四人身份、换边、撤销、Draft、记录和“再来一场”均正常。本次确认并修复 2 个真实问题；其余发现项属于明确未支持能力或平台交互差异，没有为追求表面一致而修改。
